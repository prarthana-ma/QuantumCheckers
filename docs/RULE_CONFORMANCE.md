# Engine rule conformance and limits

This document describes the local engine implementations and their boundary. It is
not a claim of bit-for-bit agreement with the upstream Cheqqers program, and results
from the toy engine must not be presented as results generated by the paper engine.

## Engine paths

| Engine | State model | Intended use |
| --- | --- | --- |
| `DeterministicToyEngine` | Per-piece square distributions with classical probabilities | Small, seeded games and reproducible experiments |
| `PaperQuantumEngine` | Sparse joint board configurations with complex amplitudes | Local paper-rule game path |

The toy engine is a checkers-like stand-in, not the published rule set. Its `live_rules`
option changes live-game movement and capture behavior; it does not turn the toy state
into a complex-amplitude state. Keep it separate from claims about paper-rule behavior.

## Paper-rule levels

The paper engine's levels are cumulative:

| Level | Implemented behavior |
| --- | --- |
| 0 | Classical draughts rules, including compulsory capture, capture continuation, crowning, terminal outcomes, and the no-capture draw counter. |
| 1 | Split pieces, movement of a selected part, and measurement when required by a capture. |
| 2 | Joint configurations preserve correlations between pieces, supporting entangled capture outcomes. |
| 3 | Merge applies the adjoint of the local split operator, allowing phase-sensitive interference. |
| 4 | Project-defined extension: coherence countdown/decoherence and optional voluntary `Observe`; this is not a level in the paper. |

The server's paper-rules path uses `PaperQuantumEngine`; archived experiment runs use
the separate toy engine. Client-facing paper-engine state exposes probabilities and
piece marginals, not complex amplitudes or phases.

## Explicit modeling choices and constraints

- The paper specifies the split operator's action on its source state, but not a unique
  full matrix for all basis states. The implementation completes that source column to
  a unitary matrix and uses its adjoint for merge. Behavior involving the other inputs
  is therefore a local modeling choice, not a uniquely prescribed paper result.
- Promotion retains path information in an internal ancilla so distinct histories do
  not become indistinguishable merely because a man became a king. The ancilla is not
  a board piece and is not rendered.
- The exact sparse state is represented and evolved in Python on the CPU. If a hardware
  sampler is configured, hardware supplies a measurement sample; it does not hold or
  evolve the persistent game state.
- Exact operations are bounded by the engine's configured branch limit (default
  4,096). Operations that exceed the limit fail rather than return a partial state.
- The engine has a safety ply limit. This operational limit is separate from the
  paper's no-capture draw rule.
- `CheqqersAdapter` remains unimplemented. No upstream code is imported or wrapped,
  and local paper-engine tests do not establish upstream parity.

## Verification boundary

The rule and property tests exercise the local implementation, including opening
positions, move legality, splitting, merging, capture/measurement, and state
invariants. Passing those tests is evidence about this code's behavior only. Exact
conformance claims require reviewing the paper's rule definitions and validating each
case against them; upstream parity additionally requires an agreed integration
approach and a working adapter.

See [PROTOCOL.md](PROTOCOL.md) for the server/client wire contract and
`qcheckers/engine/paper.py` and `qcheckers/engine/toy.py` for implementation details.
